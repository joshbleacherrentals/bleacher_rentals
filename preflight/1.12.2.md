# Preflight — 1.12.2

PR: #389
Status: passed
Signed: 2026-09-14 against 5fe6717

Same code area as 1.12.1, one PR later, same day — this is the "why is the
underlying request still slow" follow-up. `create-bill` now responds as soon
as the bill exists in QuickBooks and `WorkTrackerGroups` is updated, and
defers PDF generation + attaching it to the bill until after the response
goes out (`next/server`'s `after()`), instead of awaiting all of it before
responding. Read both commits and all five changed files — the reorder
inside `create-bill/route.ts` is the one that matters; the other four files
are the JSON-parse crash fix from last time's `parseQboApiResponse`, now
wired into both call sites.

## New in this release

- [x] **Work Trackers → a driver's week with no bill yet → Create Bill.**
      Bill creates successfully, the button flips to "Bill Created"
      promptly (don't wait for the PDF — that's the point of this change).
      Then **wait ~10–15 seconds and check the bill in QuickBooks (or via
      View Bill / the QBO bill preview in this app)** — the PDF attachment
      should still be there. This is the one real risk in this PR: the PDF
      step now runs after the response, so it's worth confirming it still
      actually completes rather than silently getting dropped.
- [x] Same flow, but **editing an existing bill** (Work Trackers → an
      already-billed week → Create/Update Bill again) — still updates the
      bill in QuickBooks correctly, same PDF-attaches-after check as above.

## Could have broken

- [x] `WorkTrackerGroups.status` still reads "Bill Created" (not stuck on
      "Creating Bill...") immediately after a successful create — the DB
      update moved earlier in the function, worth confirming the button
      reflects it right away rather than only after the PDF finishes.

## Permissions

No change. Same routes, same `requireAuth()` guard, same UI surface as

## Not testing

- `parseQboApiResponseText`'s fallback behavior (valid JSON passthrough, a
  504-specific message, a generic status-coded message for anything else,
  never throwing on malformed input) — covered by its 4 unit tests
  (`parseQboApiResponse.test.ts`), unchanged from last release.
- Deliberately forcing a real 504 to see the friendly message on screen —
  not practical to force on demand, and the actual fix here is that the
  slow step causing the timeout no longer blocks the response at all, so
  there's nothing left to reproduce it with under normal use.
- `next/server`'s `after()` itself running reliably on Vercel — a platform
  guarantee, not something a unit test can prove either way. The PDF-attach
  check above is the real-world stand-in for this.

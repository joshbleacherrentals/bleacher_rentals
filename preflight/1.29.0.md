## New in this release

- [x] As admin, open Auto Work Trackers and press **Advanced settings**. Change **Longest day** to
      600 and press Tab, then close and reopen the window. Expected: it shows 600 with
      **Changed (default: 720 minutes)** and "Last changed … by you"; **Reset to default** puts it
      back to 720 and **Default**. **If the fields are greyed out for an admin, the sync rules are
      not deployed. Stop.**
- [x] As account manager, open **Advanced settings**. Expected: the same values, every field greyed
      out, and "Only admins can change them."
- [x] As admin, set **Employees before contractors** to **Employees first**, pick a zone and week
      with no work trackers and press **Create work trackers**. Expected: the result ends with a
      "Settings: employees first · …" line. Open a created tracker: **Setup Required** is ticked,
      **Teardown Required** is ticked when it picks up from an event, and the line items show
      Hauling, Setup and Teardown at that driver's rates, adding up to the pay.
- [x] On **Driver Workload** for that week. Expected: every driver's name has **(employee)** or
      **(contractor)** under it (hover a contractor to see the vendor), and employees carry most of
      the trips. Open a driver's schedule from the ⋮ menu: each trip shows an amber teardown block
      before the haul and an amber setup block after it, an hour each.
- [x] Open **Model → Runs**. Expected: the run you just made is at the top, **In use**, with your
      name, the settings line and the version; the summary says all trips **kept**.
- [x] Open one of the run's trackers, change its driver and press **Save**. Expected: a "Why are you
      changing this trip?" box opens above the work tracker window. Type a reason and save. On
      **Runs** that trip is **edited**, shows "Driver: A → B", and your reason is next to it.
- [x] Open another of the run's trackers and press **Delete**. Expected: the same box asks why,
      with **Delete** (no browser confirm). **Cancel** leaves the tracker; **Delete** removes it,
      and on **Runs** it shows **deleted** with the reason if you gave one.
- [x] Press **Delete model drafts**, type a reason and delete. Expected: the run's drafts go; on
      **Runs** the run is **Discarded … by you** with your reason above its trips. Press **Create
      work trackers** again: a second run appears, **In use**.
- [x] In Claude with the connector, ask "Where is bleacher #<one with a GPS tracker> right now, and
      where was it yesterday?" Expected: a position and last-report time, and yesterday's stops,
      not "I can't see locations".

## Could have broken

- [x] Open a work tracker made **by hand**: change its notes and **Save**, then release a draft and
      **Save**, then **Delete** another hand-made one. Expected: no "why" box at any point; the
      driver notification preview still appears when releasing; the delete still asks the
      browser's "Are you sure…?". (The work tracker window's save and delete were rewired.)
- [x] On **Driver Data**, **Remove** a driver from the model and **Add back**. Expected: they move to
      "Removed from the model" and back. (The query behind Driver Data changed.)

## Not testing

- Who can read and write the settings, runs, run trips and feedback, including account managers
  creating them through the PowerSync upsert, admins only changing settings and discarding runs,
  the one-row and range checks, and JSON landing as objects — pgTAP
  `auto_work_tracker_runs.test.sql` (20 assertions, new in this release).
- JSON columns being parsed before upload — `jsonColumns.test.ts` and a `BackendConnector` test on
  insert and update. The connector change touches only the two listed tables, so other uploads
  are unchanged; the hand-made tracker item above exercises a normal upload anyway.
- Settings defaults, ranges, fallbacks and how they reach the solver (trip cost per objective,
  day length, setup/teardown minutes, start hour) — `settings.test.ts`, `buildSolve.test.ts`.
- Employees before contractors in the solver itself — pytest
  `test_a_trip_cost_sends_the_trip_to_the_other_vehicle_unless_it_saves_more` and
  `test_a_trip_cost_never_leaves_a_trip_out`; time on site counting towards the day — two more
  pytest cases.
- Kept / edited / deleted, field-by-field changes, timestamps compared as instants, the week's
  before/after counts — `runReview.test.ts`; the run row and snapshots written with the trackers
  — `runLog.test.ts`; feedback and discard statements — `runFeedback.test.ts`.
- Setup/teardown flags and line items, pay as their total — `writePlan.test.ts`, `siteWork.test.ts`.
- Each permission combination in the UI (viewer, accountant, maintainer, driver) — none of them can
  open Auto Work Trackers, which is unchanged, and the database refuses them (pgTAP above).
- Driver Workload's red "over 12 hours" flag — unchanged; it counts driving only and does not
  follow the Longest day setting.
- The analytics data dictionary text and the CI migration check — not user-facing; covered by
  `dataDictionary.test.ts`, the column snapshot, and the CI job itself.
- Driver mobile app — separate codebase; nothing it reads changed shape (new WorkTrackers values are
  only the existing setup/teardown flags and line items).

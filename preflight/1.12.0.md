# Preflight — 1.12.0

PR: #382
Status: passed
Signed: 2026-09-10 against 2ac81ae

Four features: the Annual Inspections queue, the new Maintainer role that owns
it, a driver's "fixed it myself" mark on a damage report, and drivers
confirming an existing report instead of filing a duplicate. Full read of
every commit and the two specs is in the PR conversation; the open questions
below came out of that read, not out of guessing.

**Before testing anything**, confirm the PowerSync sync rules in
`br_powersync` have been deployed for `BleacherAnnualInspections` and
`Maintainers` — the migration commit says so explicitly: without them the
queue page is silently empty and a maintainer sees "no roles assigned," which
looks like a bug rather than a missing deploy step.

## New in this release

- [x] **Sidebar → Quality Assurance → Annual Inspections**, as an admin. Queue
      sorted `unscheduled → overdue → critical → warning → ok`. Click a row,
      record an inspection — next-due prefills to one year out, is editable,
      accepts a PDF and a note — and the row moves to `ok`.
- [x] **Team → + New User → Maintainer.** Create one, sign in as them: they
      land on `/annual-inspections` (no dashboard), see the sidebar count, and
      recording an inspection there survives a reload (proves RLS accepted the
      write, not just the local DB).
- [x] Same maintainer: the sidebar count clears on opening the page, and a
      second visit only highlights bleachers that crossed a threshold since
      the first.
- [x] As an **account manager**: Quality Assurance has no Annual Inspections
      link and `/annual-inspections` redirects away, but
      `/assets/bleachers?edit=<n>` still shows the inspection block and
      recording from there still works.
- [x] As a **viewer**: can open the queue and a bleacher's inspection history,
      no Record button anywhere, no sidebar count.
- [x] **Damage Reports → open a report a driver has marked fixed** (or fake it
      by hand in Studio: `fixed_by_driver = true`). "Fixed by [name] on
      [date]" shows, **Mark as Resolved** sits beside Create Maintenance to
      Resolve, and clicking it resolves the report without creating a
      maintenance event. **Remove fixed mark** clears it back to normal.
- [x] **Damage Reports → a report two or more drivers acknowledged** (seed via
      `DamageReportAcknowledgements` if nothing real exists yet) shows
      "Confirmed by N drivers" with names and dates, on both the list card and
      inside the modal.
- [x] **Team**, with only a Maintainer role on an account: the "Incomplete
      User Setup" banner does not list them.

## Could have broken

- [x] **Admin and viewer** still see Annual Inspections in the sidebar (it's
      only the notification badge/highlight that became maintainer-only, not
      the page) and get no count and no row highlighting.
- [x] Every other role's Quality Assurance dropdown is unchanged — admin
      still sees all four links, an account manager still sees Damage
      Reports / Inspections / Repairs.
- [x] Existing damage report flow — open an **unmarked** report, "Create
      Maintenance to Resolve" is the only button, no "Mark as Resolved", no
      confirmation panel.
- [x] Regular photo uploads on a damage report from the **driver app** still
      go through — the new driver-side column fence on `DamageReports` (the
      "may only touch fixed\_\* columns" trigger) has an explicit carve-out for
      the server's own `photos_uploaded` recompute; worth one real upload to
      confirm it wasn't broken by the new trigger.

## Permissions — needs your answer before this ships

1. **Both specs are still marked `DRAFT — awaiting approval`**
   ([bleacher-annual-inspections.md](docs/specs/bleacher-annual-inspections.md),
   [maintainer-role.md](docs/specs/maintainer-role.md)) even though the code
   shipped. Worth stamping "Approved" once you've confirmed the two items
   below, so the doc matches what's actually live.

2. **A maintainer's `/assets` grant is wider than the spec describes.**
   [`accessConfig.ts`](src/features/userAccess/accessConfig.ts) gives
   maintainer the path `/assets`, and route matching is prefix-based
   (`pathname.startsWith(p)` in
   [useAccessRedirect.ts](src/features/userAccess/hooks/useAccessRedirect.ts)).
   That opens `/assets/other-assets` and `/assets/documents` to a maintainer,
   not just `/assets/bleachers` — nowhere in the spec, the permission matrix,
   or the new test (`accessConfig.test.ts:21`) says a maintainer should see
   Other Assets or Asset Documents. Intended, or should this be narrowed to
   `/assets/bleachers`?

3. **A `developer` can read damage report acknowledgements.** The RLS select
   policy on the new `DamageReportAcknowledgements` table
   (`20260910140000_damage_report_acknowledgements.sql`) includes
   `{admin, account_manager, developer, viewer}`. The Damage Reports entry in
   `permissionPageData.ts` says "Developers do not have access to damage
   report data" and there's no separate matrix row for acknowledgements.
   Deliberate (mirroring a role list copied from somewhere) or should
   `developer` come out of that policy?

## Not testing

- Pure date/status logic (`inspectionStatus`, `isNewSinceLastSeen`,
  `nextDueFromInspected`, `thresholdDates`) — covered by unit tests with
  boundary and leap-year cases already in the diff.
- RLS on `BleacherAnnualInspections`, `Maintainers`, and
  `DamageReportAcknowledgements` per role, including cascade deletes — covered
  by the three new `supabase/tests/*.test.sql` files.
- The `fixed_by_driver` mark itself and the acknowledgement UI — both are set
  from the **driver mobile app**, a separate codebase (`br_driver`). Nothing
  to click here; the web side only reacts to rows that already exist.
- `useIncomplete` picking up the new Maintainer join correctly — has its own
  Vitest suite (`useIncomplete.test.ts`), and is also covered by the manual
  "Incomplete User Setup" check above as a belt-and-braces pass.
- The one-click "Mark as Resolved" being available to any account manager on
  any report, not just ones they created — this is how `DamageReports` writes
  already work today (the DB's update policy has never been scoped by
  creator; the client-side "own reports only" rule is UI-only). Not a
  regression this PR introduces, and pre-existing, so left off the questions
  above — flagging here in case it's news to you.
